# New set ingestion and launch: play-by-play

This is the **permanent operator guide** for admitting a new regular MTG set to Pack One. Use one **finite, set-specific launch issue** for the release checklist and evidence, and close it after the first public Daily is verified. Do **not** maintain a perpetual "new sets" issue. Example: [Star Trek (TRK) launch #1728](https://github.com/killjoy00/mtg-ev-analyzer/issues/1728).

The authoritative technical contracts remain [Corpus Operations](CORPUS-OPERATIONS.md), [Latest/Main Daily selection](LATEST-DAILY-SELECTION.md), [card art](CARD-IMAGE-MAINTENANCE.md), [trophy-deck catalogs](../corpus/trophy-decks/README.md), [card strength](../corpus/card-strength/README.md), [Traditional admission](TRADITIONAL-PUZZLE-ADMISSION.md), and [season handling](../worker/draft-run-season.mjs). This guide sets the **order, operator actions, verification evidence, and stop conditions**; it does not relax those contracts.

## Responsibility and release rule

- **AI / reviewed automation:** inspect the official sources; prepare code, metadata, guides, and PRs; run offline tests and non-destructive rehearsals; ingest, build catalogs, rescore, verify, deploy through authorized workflows, monitor and report. An agent needs valid connected permissions or an already-authorized workflow for each privileged action; never imply it can use credentials it does not have.
- **Owner:** may approve the release/communications as necessary and may personally engage with players. **The owner does not review, grade, sample, or rate individual puzzles.** Do not create a manual puzzle-review gate, a UAT survey, or a request to run scripts on the owner's machine.
- **Automatic acceptance replaces subjective puzzle review**, but it can establish technical/source quality, not prove that every individual puzzle is fun. If objective tests fail, stop and fix the source/process or wait for fresher archives. Do not lower corpus thresholds, change model scoring, cherry-pick a weak sample, or bypass safety gates to meet a date.
- **No app-store submission** is needed for a normal data-backed set becoming Live. The backend provides set metadata and puzzles to existing clients. Hard-coded native labels (e.g. the Insights set-name map) may need a separate future app update; assess this as presentation polish, not a reason to block the server-side release.

## Release clocks and rough effort

These are **planning ranges, not measured SLAs**. They exclude waiting for 17Lands and do not guarantee a specific day.

| Milestone | Typical planning allowance | Owner participation |
| --- | --- | --- |
| Pre-data preparation: identity, rehearsal, launch copy, guide shell, checks | 4–8 hours of agent/CI elapsed work | Optional message approval |
| Official draft + game archives appear | External dependency, unknown timing | None |
| First development Candidate and health/canary | Budget 1–3 hours; Corpus Operations job has a 180-minute limit | None |
| Production Candidate (identical artifact) | Budget 30–90 minutes; retries if blocked | None |
| Decklists, card strength, feature scoring, art and automated acceptance | Budget 2–6+ hours, depending on archive size and release jobs | None |
| Development and production activation + smoke | Budget 30–90 minutes | Authorized release decision if required |
| First new-set Daily | Next scheduled Pacific date after activation; generated around **00:07 Pacific** | None |
| Initial monitoring and posts | Day of first verified Daily | Optional posts/community replies |

Budget **one to three calendar days after both archives are usable** for a clean, quality-first release; upstream changes, failed gates, or costly backend image propagation can take longer. Do not promise public dates before the objective evidence exists.

## Phase 0 — Before the data arrives

1. **Open a finite issue and pin source facts.** Record set code, official name and Arena release date from Wizards and Scryfall; distinguish Arena release from public 17Lands archive publication. Link this guide; define the first-Daily/season closeout gate. Do not assume that missing archives imply a pipeline bug.
2. **Prepare names and rendering.** Add the Scryfall official name to `data/set-display-names.json`, since otherwise the web Draft Run heading shows a code. Audit other hard-coded names, including `mobile/src/screens/insights.tsx`. Existing Daily/Practice/Latest selectors read Live set metadata; do **not** add a new set to an older manual release list or make the set Live early.
3. **Research special printings, but do not guess.** Read Wizards' collecting guide and Scryfall's set/printings metadata. Document booster-contained bonus sheets, Arena-only substitutions, exact card-name variants, double-faced cards and possible same-name collisions. The resolver prefers main-set ordinary/base printings, then verified Arena booster-source printings released with that set, then an ordinary historical printing. Collector-only/Commander/Alchemy/Jumpstart products are not automatically eligible. The reviewed `corpus/draft-run/card-printings.json` is the change-control record for non-main-set images. Verify actual draft contents against the 17Lands archive after arrival before accepting an image mapping.
4. **Rehearse without touching an active set.** Run code-level importer, source snapshot, quality gate, Candidate-canary and selector tests with existing fixtures / isolated disposable development state; confirm the production promotion provenance guard and workflow inputs. Never publish, pause, switch, or overwrite a Live environment just for rehearsal. Check that protected GitHub workflows, Neon credentials, R2 requirements and deployment-size limits are available.
5. **Prepare automated launch-quality reporting.** Require a report of: qualified trophies and exclusion reasons; 8-pick trajectory completeness; unique sources and each P1P1–P1P8 band coverage; finite normalized probabilities and card metadata/image coverage; score-floor exclusions; selection-feature completeness including strength SHA and deck-main membership; a deterministic dry-run of eight-pick Latest and Mixed selection with repeat exclusions, Easy and contested pools, and no silent fallback. Existing CI/Candidate health/canary gates cover part of this; add focused tests or a preflight for uncovered items rather than pretending a manual puzzle review can substitute.
6. **Prepare the content shell.** Draft a cited set guide from Wizards' official mechanics, archetypes and card sources. Do not invent 17Lands win rates, pick percentages, or a "best archetype" before the data exists. Prepare the Practice announcement and channel-tracked website links and posts for Patreon, Bluesky, Discord and Reddit, without publishing claims that the set is Live.
7. **Watch both 17Lands inputs.** [Public datasets](https://www.17lands.com/public_datasets) must have **both PremierDraft draft and game archives**. The current reviewed `Corpus Operations` workflow runs **Mondays at 07:23 UTC** and can be manually dispatched; it is not an automatic daily arrival watcher. For a new launch window, create a lightweight read-only readiness check or deliberately recheck the catalog daily. Do not schedule recurring full imports, expensive scans or production writes merely to check availability. Alert with source URLs and hashes/metadata when both files are ready.
8. **Check capacity and release ownership.** Review open Neon compute/egress or backend incidents before importing millions of rows or refreshing art. Confirm who can execute an authenticated Admin lifecycle change, and reserve the right to postpone if operational health is degraded.

### Example: Star Trek / TRK (November 2026)

Official Wizards sources confirm **TRK** (base set), **SDS** (Stardates cards that can occur in Play Boosters), and **TRC** (Commander cards); Arena Premier Draft began November 10, 2026. Only cards actually present in the **Arena draft data** are eligible for the new puzzles. At the November 20 source check, 17Lands public datasets listed FRA but **not TRK PremierDraft**. Recheck rather than hardcode an anticipated publication date. The set-specific actions and closeout live in [#1728](https://github.com/killjoy00/mtg-ev-analyzer/issues/1728).

## Phase 1 — Official archives available: build the development Candidate

9. **Verify inputs.** Confirm 17Lands published the PremierDraft draft **and game** files; verify access, content/schema, hashes/ETags/last-modified, official Scryfall identity and release chronology. Incomplete/failed files are a waiting state, not launch approval. Missing replay archive is *not* itself a blocker (FRA has none).
10. **Stage the development import.** On reviewed `main`, dispatch [Corpus Operations](../.github/workflows/corpus-operations.yml) with `target=development` and no `validated_run_id`. It discovers new archives, builds qualified-trophy decisions with the current frozen **model implementation**, validates hashes/ledger accounting, loads an immutable snapshot and runs Candidate health and gameplay canary. Save the **successful development run ID, head SHA, source hashes, snapshot ID, import disposition counts and gate report**.
11. **Enforce the existing corpus gates.** A passing import has at least **50 qualified trophies**, **200 usable decisions**, at least **16 distinct independent medium/hard source drafts at each served pick** (the easy fallback is defined by the existing policy), zero invalid included trajectories, <=25% exclusions with no >10-percentage-point increase from prior verification, complete included card name/type/image metadata, finite normalized probabilities, >=200 held-out first-eight examples and **ECE <=0.15**. The exact versioned gates in `corpus-quality.mjs` remain authoritative. **Blocked/Awaiting corpus is not a Candidate and cannot serve.** Wait for a changed upstream archive or repair a real defect; don't weaken the checks.
12. **Protect provenance.** Do not edit `scripts/corpus_promotion_provenance.py`'s ingestion-relevant paths between the successful development artifact and production staging. If relevant code changes, rebuild and revalidate development. The 90-day artifact retention is a recovery option, not permission to publish stale evidence.

## Phase 2 — Matching production Candidate and quality prerequisites

13. **Stage exactly the development artifact in production.** Dispatch Corpus Operations with `target=production` and `validated_run_id=<successful-development-run-id>`. It verifies original builder SHA and ingestion revision, validates the same payload and scans the production Candidate. No activation occurs. If the artifact is gone, rerun development with `recovery_sets=<set-id>` and use its new validated run.
14. **Build the game-data-derived catalog and strength table.** Use the official game archive pinned to the import to generate `corpus/card-strength/<set-id>.json` (the reviewed `gih-shrunk-400-v1` method) and trophy-deck catalogs using **actual imported source inventories**, the last observed game deck, and Scryfall names. Follow [trophy-decks](../corpus/trophy-decks/README.md) and [card strength](../corpus/card-strength/README.md). Reports must distinguish missing game records from incomplete/ambiguous decks. Import always runs the mandatory *deck coverage check*, but the check does **not** guarantee a catalog exists or impose a coverage minimum. Record the actual percentage and treat poor context coverage as an explicit product risk.
15. **Release catalog/strength inputs and score selection features.** Review/deploy the new catalog and strength inputs through the standard PR/release path; respect the backend function package-size limit. `Score puzzle selection` ([workflow](../.github/workflows/score-puzzle-selection.yml)) on development then on production using the validated development scoring run ID. New imports *attempt* import-time scoring, but a set not yet present in the strength/deck catalogs needs a post-catalog backfill. **Verify every serving P1P1–P1P8 puzzle has a feature row tied to the current strength-table SHA, including clear-Easy fields**. The Latest Set stakes and clear-Easy guards otherwise fall back, potentially for the whole Daily; do not silently launch with the old selector.
16. **Verify card identities and printings.** Inspect all set-visible cards, not only checked-in samples; check main-set art, bonus sheets and double faces against Scryfall and actual Arena draft contents. If the full image-policy audit proposes additions to `corpus/draft-run/card-printings.json`, review and merge the proposed record and run the [guarded image workflow](CARD-IMAGE-MAINTENANCE.md) before activation. A full refresh can be expensive (historically >1 hour); avoid running it merely to repair mismatched Traditional art. Verify zero unresolved served names/blank images, the expected art for bonus printing cards and actual backend display.
17. **Run automated acceptance, not an owner puzzle review.** Exercise deterministic Latest and Mixed eight-pick selection against the Candidate in isolated test mode, including distinct source rules, difficulty pools, 28-day decision and 7-day source repeat windows, late-land and main-deck filters, credible contested options, clear-Easy cases and fallback flags. Require valid histories/packs/choices, no impossible outcomes, no score normalization failure, and no regression on existing Live sets. Produce a short evidence report with exact counts and **pass/fail**, and hold launch for defects. **Do not assign the owner a sample of puzzles to rate.**
18. **Decide readiness from evidence.** Before activation, require: fresh passing exact-snapshot corpus health; matching dev/prod Candidate; current model/corpus; approved image source record; released deck/strength inputs and scored selection features; passing automated canary/selector tests; stable production capacity. Otherwise leave the set Candidate and continue investigation. A human can authorize publication but is **not** responsible for judging individual decisions.

## Phase 3 — Activation and the actual launch day

19. **Publish development first, then production.** In [Admin → Corpus Operations](https://packone.pro/admin/?area=corpus), authorized operator changes **Candidate → Live** in development, then production. Evidence for exact manifest/gate must be younger than **seven days**. Otherwise dispatch the targeted `Corpus snapshot health check` for that snapshot. Do not use retirement as rollback; retirement is terminal.
20. **Run serving smoke / prewarm on each target.** Dispatch `Corpus activation serving smoke` with set ID and snapshot ID. Check current active snapshot, single-set Custom practice, pack reroll, generated game/puzzle payload and response latency. Its checks cover the selectors affected by newest-set chronology. Never assume a successful data load equals a successful serving deployment.
21. **Wait for the next scheduled Pacific Daily.** Dailies are generated around **00:07 Pacific** and are pinned. A newly Live latest regular set should be all eight choices of the **next** Latest Set Daily; mixed Daily should include **two** latest-set decisions. The *first* new-set Latest Set Daily automatically establishes the new leaderboard season; **do not reset tables or alter already generated schedules**. If activation missed the cutoff, shift the external launch date.
22. **Verify production before any announcement.** Read the real public Latest Set Daily, Mixed Daily, Custom Practice and season standings on the web and (when available) installed mobile apps. Verify correct set name/art, playable eight decisions, share/result paths, the expected Daily selection rule, the expected season start, preservation of old histories, and no current launch alerts. Client display-only omissions are tracked separately.
23. **Release communications after verification.** Only now update the Practice callout and publish any approved set guide, Patreon/Reddit/Bluesky/Discord messages and creator links. Use channel-specific website campaign URLs; credit 17Lands accurately without implying partnership. Verify social jobs actually published rather than equating queued/successful workflow with a live post.
24. **Observe the first day and close the one-time issue.** Check gameplay starts/completions, dropped/error rates, database compute/egress, scheduled Daily consistency, reports, and user feedback. Record source/version hashes, successful runs, the first Daily/season day, marketing links, and any deferred follow-ups. **Close the set-specific issue after those release criteria**, even if unrelated enhancements remain.

## Failure and follow-up paths

- **Missing game file / too few qualified trophies / blocked health:** wait for the changed 17Lands archive; do not force a Candidate or lower thresholds.
- **Failed production artifact provenance:** never reuse a mismatched payload; re-run development from reviewed main and promote the newly validated artifact.
- **Missing strength table / incomplete feature rows:** leave Candidate; build the table, publish it, run focused development/production `Score puzzle selection` and verify its SHA matches before Live.
- **Low trophy-deck coverage:** record exact denominator and missing reasons; rebuild from pinned game data where possible. Missing decks are allowed by the importer, but cannot be misrepresented as comprehensive context. Confirm selectors that require deck evidence have sufficient supply.
- **Image-policy mismatch:** use the reviewed printing-record proposal and appropriate guarded image path. The full refresh covers database-only environments such as FRA; targeted repair does not. Traditional-to-Premier display drift uses the **Traditional-only** repair/check.
- **A newly published archive replaces the source later:** stage a new immutable development Candidate; validate and stage it in production; only then switch the Live snapshot explicitly. Existing pinned games remain readable.
- **Critical post-activation issue:** hold communications, investigate, and use Live → Paused for new starts if warranted. Do not delete scores, mutate historical sources, or rewrite the current fixed Daily.
- **Traditional Draft:** measure against the approved Premier model as a separate additive source and publish only after its own fixed gates. It is **not** part of the initial Premier launch; a failed whole-window protocol cannot be represented as passed by post-hoc narrowing.
- **New grading model / app binary:** separate versioned projects, not a requirement for the set-data release.

## Release evidence template for a set-specific issue

Record links (not secrets or player identities) to: official Wizards/Scryfall set facts; 17Lands draft/game file metadata; reviewed implementation/config PRs; development Corpus Operations run and Candidate health; matching production Candidate run; catalog/deck coverage and strength SHA; selection-feature development/production score jobs; image-policy decisions and release; automated eight-pick acceptance; dev/prod activation smoke; first public Latest and Mixed schedules plus season start; initial monitoring; communications. Note **PASS / BLOCKED / DEFERRED** with a reason for every gate. There is **no owner's puzzle-review field**.
