# Results and news delivery

This extends the November 16 controls launch. The notice launch and its fourteen-day publication cutoff are immutable. This sender never includes another player's name, profile link or individual results, and does not publish named results.

## Delivery

- Weekly personal results: Monday at 10 a.m. America/Chicago, for the previous Monday–Sunday Pacific game dates. The ten-minute trigger evaluates local Central time through DST. It uses the existing weekly leaderboard scoring (best three Dailies divided by three), standings lineage and eligibility. A hidden public identity receives its own numerical summary without a public rank. Accounts with no activity receive no results digest.
- Season results: at 10 a.m. Central after an existing season closes, using the same season rating policy and each recipient's own results. No historical seasons are backfilled when delivery is enabled.
- News/offers: Owner-only drafts in Admin → Users → Results and news emails. Saving a draft sends nothing. The owner previews the exact escaped subject/body and explicitly approves that preview. Approved campaigns enter the next ten-minute run, with a 24-hour delivery window. No copy is invented or automatically approved. Cancellation stops messages not yet handed off.
- Every message requires current explicit Results and news consent, a verified unchanged destination, no suppression, and the existing deletion lock. A campaign excludes accounts that opted in after approval. Daily reminder consent is independent.
- Every provider handoff goes through `prepareResultsEmail`, with the private postal footer and signed scanner-safe/one-click unsubscribe links. Envelopes, addresses, names, provider bodies and individual ledger rows never enter public logs or artifacts.

The private ledger uniquely claims one delivery per campaign/account across concurrent jobs. The provider gets a stable idempotency key. Accepted sends and signed delivery events are recorded without message contents. An ambiguous handoff or abandoned claim becomes `uncertain` and is not automatically retried, including after the provider's idempotency window. Inspect aggregate unconfirmed counts before considering any individual private reconciliation; never blindly resend a campaign.

Authenticated events are monotonic: late sent/delivered events cannot undo a bounce/complaint. Existing Daily suppressions also deny Results/news admission. Account-deletion commitment removes preferences, admissions and all delivery rows immediately, including preparing rows, before normal identity cleanup. Generic campaign copy contains no identity; a targeted delivery-check campaign is deleted with its owner. Already handed-off emails cannot be recalled.

## Guarded rollout

1. Merge the implementation after exact-head required and affected checks, including real PostgreSQL concurrency/deletion tests and actual Chromium owner-control acceptance.
2. Prepare a separate reviewed `.github/secure-auth-release-request.json` and enable `.github/results-email-delivery.json`. Use the existing protected `pack-one-mobile-release` environment and development-then-production release. No direct production SQL or unguarded deployment.
3. The protected configuration step reads `PACK1_RESULTS_POSTAL_ADDRESS` from the same-named Environment secret (automatic log redaction), or reads the private Environment variable at runtime through GitHub's authenticated API. Never interpolate the ordinary variable into workflow `env` or `run`: the runner prints those before masking can execute. If the job token cannot read the variable, use the Environment secret. Optional sender variables default to `Pack One` and `news@packone.pro`. Results API credentials can reuse the existing Pack One reminder/account-deletion sending credential. A full-access `PACK1_RESULTS_RESEND_ADMIN_KEY` can configure the dedicated webhook when the sending key is restricted. An already provisioned dedicated `PACK1_RESULTS_RESEND_WEBHOOK_SECRET` can instead be supplied privately. Never commit values.
4. The configuration script creates or reads only the dedicated results webhook, without rotating another secret or touching another endpoint. Ambiguous creation reconciles by read. It masks private values and passes them only through the runner environment into the reviewed backend deployment. Development sending remains off.
5. After production schema, functions, gateway and retained timing verification, the release reconciles only `pack1-results-email` on the production branch. Existing Daily, social and deletion triggers are untouched. The shared scheduler inventory also contains this trigger for an intentional all-scheduler disable.
6. General sends remain blocked until an Owner's explicitly requested delivery-check email produces a valid signed delivered event. The account must already have a verified address and Results and news on; the check never changes consent. Admin → Users → Results and news emails → **Send me a test email** sends to that Owner only, even while general delivery is gated. A signed confirmation unlocks scheduling for that exact sender/postal/webhook configuration. Changing those private values requires a new delivery check.
7. Verify the private aggregate delivery status and next trigger invocation. Do not report delivery active from a successful configuration or provider acceptance alone. A required environment approval, missing configuration or missing actual delivery proof remains a blocker.

Native build distribution remains separately guarded. Apple App Privacy must declare the optional advertising/marketing use of Email Address before public release; Google Play's matching email-use purposes were already accepted. No app submission, testing-track or named-publication change is implicit in an email campaign.

## Validation

`tests/results-email-delivery-postgres.mjs` exercises real migrations, concurrent claims, consent/address changes, shared suppression, authenticated event ordering, delivery-check gating, private standings, exact draft approval and deletion commitment. `tests/results-email-admin-e2e.mjs` uses the actual owner UI with synthetic APIs. Unit tests cover Central/DST scheduling, escaped content, private configuration, webhook reconciliation and scoped scheduler control. The existing results privacy, fourteen-day launch, deletion, reminder, gateway and native checks remain required for their affected paths.
