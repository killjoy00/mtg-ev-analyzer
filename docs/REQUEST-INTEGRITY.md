# Request and identity integrity

Reviewed 2026-09-20. Backend changes require deployment after migration 0013; merging code does not deploy Neon Functions.

## Implemented protections

- Both legacy and growth APIs use `worker/request-json.mjs`: JSON objects only, valid UTF-8, at most 128 KiB measured while streaming, with explicit 400/413/415 responses. Session creation validates before token/identity work; invalid bodies no longer silently create guests.
- Analytics submission requires a signed guest/player token. Browser submissions cannot create server-owned account, public-profile, achievement or Draft Run start/completion milestones. Legacy browser events such as `game_start`, `daily_completed` and `challenge_complete` remain descriptive client observations; they are not proof of scoring or unique humans. Authoritative results remain in `scores` and `game_results`.
- Atomic database counters limit a player to 300 accepted analytics events per minute, 60 legacy career-result submissions per ten minutes, and 30 new Draft Run/Cube sessions per ten minutes. A resumed Daily returns before consuming a creation limit. Answering/resuming existing games remains available. Counters reuse one row per player/scope, work across function instances, reset after their window and return HTTP 429 with `Retry-After`.
- Production CORS excludes localhost by default. An isolated local-development function may set `PACK1_ALLOW_LOCALHOST=1`; production should leave it unset. CORS is a browser policy, not authentication or an abuse firewall.
- Growth JSON responses use `Cache-Control: no-store`; unexpected legacy database errors return a generic error. Fresh legacy signing-key initialization uses cryptographic random bytes, preserving any existing key.
- One `game-date.mjs` implementation owns Eastern dates for frontend, Today, both backend modules and legacy aliases. Misnamed UTC callers are removed; DST and midnight regression cases cover every entry point.
- Today refreshes on a completed result, return to the page and a date change. Old asynchronous results cannot overwrite newer state. Today and Profile subscribe to the common rendering lifecycle, now included in the architecture gate.

## Password recovery integrity

- Password-reset requests are signed-out by design but still require the authoritative Pack One origin policy. Production recognizes `https://packone.pro`, `https://api.packone.pro`, and `https://magic.planitnow.us`; localhost is added only with explicit `PACK1_ALLOW_LOCALHOST=1`. `requireTrustedOrigin()` has no implicit fallback.
- The recovery callback is server-owned configuration. Production always supplies `https://packone.pro/reset-password/`; isolated Auth QA supplies `http://localhost:4173/reset-password/`. Request bodies, query strings, `Origin`, `Referer`, host/forwarded-host headers, cookies, fragments, localStorage, and sessionStorage cannot choose it.
- Anonymous reset requests are throttled by a deterministic HMAC-SHA-256 of the normalized email using the dedicated server-only `PACK1_RATE_LIMIT_SECRET`. Raw email and plain SHA-256 email digests are not persisted as limiter identity. The limiter expires rows and fails closed before provider invocation when the secret is missing.
- Public request-reset responses do not disclose whether an email exists or whether it has a password credential. Provider-specific 4xx account lookup behavior is collapsed to the same generic public response; provider outages remain generic temporary failures.
- Recovery credentials are accepted only by the reset-completion endpoint, are not logged or persisted by Pack One, and are removed from the browser-visible URL/history as soon as the reset page loads. A successful provider reset revokes every Pack One first-party session for the resolved Auth user; malformed, expired, reused, policy-rejected, or provider-failed resets revoke none.
- Auth provider selection is deployment/runtime configuration. Production defaults to production Auth; the static local development configuration selects the isolated QA Auth provider. Browser query/hash/cookie/storage input is not an environment selector.

## Signed-in credential management integrity

- Credential-management mutations are deliberately different from signed-out recovery. They require an authenticated Pack One first-party account session, `allowLegacy:false`, CSRF validation, and the explicit trusted-origin policy before credential work begins. A legacy Neon bearer/session header cannot authorize password or email changes.
- The authenticated Auth UUID is derived only from the validated Pack One session. It is stored directly as the account limiter dimension; client-supplied user IDs, target emails, headers, body padding, redirect values, or other superficial request fields never select a fresh account bucket.
- Current-password verification has one account-global failure budget shared by every credential route that verifies the existing password. The current policy allows 8 verification attempts per 15 minutes globally per Auth user. Password change also has a defense-in-depth account-plus-network bucket allowing 5 attempts per 15 minutes.
- The network dimension originates only at the Cloudflare gateway from `CF-Connecting-IP`. The gateway normalizes the network, HMAC-SHA-256 hashes it under its server-only quota key, and authenticates the resulting digest to the worker with a second HMAC proof under `PACK1_RATE_LIMIT_SECRET`. The worker persists only the HMAC digest. Raw client IP, `X-Forwarded-For`, and caller-supplied forwarding headers are not limiter identity.
- Account-global throttling does not depend on network-secret configuration. Sensitive mutations nevertheless fail closed before provider invocation when the authenticated gateway network proof is missing, malformed, or invalid. A local throttle decision prevents all relevant Neon Auth calls.
- A successful current-password verification clears only the shared account current-password failure bucket immediately after the provider accepts that password. Wrong current password, malformed requests, throttled requests, and provider verification failure do not clear it. A later new-password policy rejection therefore does not punish a legitimate user with accumulated current-password failures; the account-plus-network submission bucket still ages out naturally.
- Password change re-authenticates against Neon Auth using the validated Pack One user's server-derived email and the submitted current password. It never accepts a client-selected Auth identity or email. The temporary provider session is destroyed after the attempt. Only provider success revokes all Pack One first-party sessions and clears Pack One account cookies.
- Google-only accounts are identified from the provider account rows and are shown a provider-aware state instead of a broken change-password form. Password management does not create credentials, unlink Google, or mutate provider identity.
- Email-change submissions use separate account-global and account-plus-network purposes so target-email rotation cannot create fresh buckets. The staged policy allows 6 submissions per account per hour and 4 per account-plus-network per hour. Successful email submissions must not clear those abuse buckets; they age out by window. **Provider capability gate:** as verified against isolated Neon Auth QA on 2026-09-21, Managed Auth currently returns `Change email is disabled` for Better Auth `/change-email`, and Neon's exposed Auth configuration does not offer Better Auth's required `user.changeEmail.enabled` switch. Pack One must not fake a verification-send success or directly mutate `neon_auth.user.email`; the email mutation remains gated until Neon exposes a supported change-email capability.
- The gateway literal allowlist contains the credential-management route names, but Pack One application code remains responsible for authentication, CSRF, Origin, identity derivation, callback ownership, throttling, provider-error normalization, and session policy. No provider token, password, CSRF value, raw network identifier, or rate-limit secret is browser-persisted or intentionally logged.

## Remaining ingress and account work

The [gateway operations and rollout plan](EDGE-OPERATIONS.md) now provides a private preview Worker, opt-in backend origin authentication, durable network quotas and a reviewed-PR operating workflow. These controls are not enabled on the existing development/production functions. Public session cookies and revocation still require the staged migration described there.

Cloudflare inspection can run through the [read-only GitHub Actions setup](CLOUDFLARE-ACCESS.md), either manually or by merging an audit request into `main`. The audit needs a zone-scoped `CLOUDFLARE_AUDIT_TOKEN` secret; it does not grant deployment access or change live settings. Verify its actual inventory before choosing the first-party routing and origin-protection design.

These limits do **not** stop a caller creating many new guest identities. `/v1/session` still needs a trusted IP/edge quota, and expensive public health/reporting endpoints need ingress protection. Determine which proxy overwrites the client IP header, block direct-origin bypass, and verify spoofed headers before enforcing a quota. Do not trust arbitrary `X-Forwarded-For` or claim a function-local memory counter protects a serverless deployment. No new infrastructure, guessed proxy header or opaque challenge has been enabled.

Guest leaderboards identify devices/accounts, not verified humans. Optional account claiming alone cannot prevent multiple-account answer harvesting. Keep guest access while deciding whether competition warrants a separate verified board and what verification actually means. Never seed simulated scores as players or treat duplicate display names as verified identities.

Tokens still live in localStorage and player tokens remain long lived. Consolidated escaping reduces drift but is not an XSS or revocation solution. A first-party HttpOnly cookie requires a compatible first-party API/auth proxy and a reviewed CSRF/session/revocation flow: the current Pages frontend and Neon API/Auth hosts are different sites. Do not switch to SameSite cookies without verifying cross-site browser behavior. The API is not a place to store account credentials in GitHub.

The release gate uses an expiring isolated Neon branch for concurrency, quota expiry, spoofed milestone and response-header tests. Its parent can lag merged code: the gate therefore explicitly replays the repeatable release backlog (0012–0015, including metadata-only serving statistics), plus newly added PR migrations. Keep that list synchronized until the parent is promoted; never assume a Git merge updates the database or blindly replay historical migrations. This setup modifies only the disposable CI branch.

Apply migrations 0012 and 0013 in order and deploy all affected functions in development before production. Existing counters can remain during a function rollback. Trusted edge configuration and real-device authentication/sharing require access beyond the repository workflow.
