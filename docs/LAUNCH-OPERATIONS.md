# Launch response and usage controls

The production launch watcher requests a five-minute GitHub Actions schedule, but GitHub schedules are not a delivery guarantee. Alert-mode runs therefore persist a sanitized gateway-log coverage watermark in issue #596 (`[launch watcher] Coverage state`) instead of assuming the current run arrived on time. Each threshold calculation is still exactly a 15-minute window: window endpoints advance in five-minute steps, a two-minute settlement delay avoids treating the newest log edge as complete, a first run bootstraps two hours, and every later run replays the most recent 30 minutes for late log arrival before moving forward. Catch-up remains bounded to 30 new windows (2.5 hours) per run. If a run ends with recoverable backlog, it routes a `coverage_pending` incident and immediately dispatches the same workflow as a serialized continuation instead of waiting for another best-effort cron delivery. Continuations preserve the existing concurrency group, increment a reviewed depth counter, and stop after 12 chained passes. Dispatch failure or depth exhaustion routes `coverage_continuation_failed` and fails the run; the next independent schedule can start a new bounded chain. Recoverable coverage incidents close automatically once no corresponding condition remains. A `telemetry_unavailable` incident also closes automatically after a later run proves the coverage watermark persisted, no catch-up windows remain, no telemetry window failed, coverage is recoverable, and the run recorded no telemetry errors.

Coverage advances only through the last fully inspected new window. A failed, truncated, schema-invalid or inaccessible replay/catch-up interval stops forward progress; a later run starts from the durable watermark again. The workflow's concurrency group serializes alert-mode executions, and the state update re-reads and monotonically merges the issue body so a stale writer cannot move the watermark backward or erase recorded alert-window evidence. Duplicate retained events are keyed by Cloudflare event ID inside each query. Recent successful windows are deliberately replayed so an event that arrives late can still breach its original 15-minute threshold.

Workers Logs retention is plan-limited. The watcher uses the documented three-day minimum retention as a conservative recoverability bound even if the account may retain more. If the first missing 15-minute calculation requires logs older than that bound, the run reports `coverage_unrecoverable`, does not advance across the gap, routes a category-specific incident, and fails. Operators must not infer healthy coverage from a later current-window query after such a gap.

The existing independent Neon `pack1-account-deletion-maintenance` Function Trigger also checks the public sanitized coverage watermark after its deletion-maintenance work. If issue #596 is absent/invalid/inaccessible or `covered_through` is more than 30 minutes behind the trigger's edge-attested scheduled time, `pack1growth` logs a structured `launch_watcher_stale` event and returns 503 for that trigger invocation.

The same Neon invocation now owns a bounded recovery path for delayed or missing GitHub schedule materialization. It does **not** reimplement launch monitoring: it dispatches the existing `.github/workflows/launch-alert.yml` root with `continuation_depth=0`, after which the workflow's existing concurrency group, monotonic #596 state, replay windows, retention bound and #644 continuation chain remain authoritative. Recovery state is stored separately as `launch_watcher_recovery_dispatch_v1` in `settings` and is claimed with compare-and-set semantics so concurrent Neon invocations cannot intentionally create duplicate roots. A stale episode is limited to three independent root attempts. A failed dispatch may retry on the next ten-minute Neon interval; an accepted dispatch that shows no coverage progress waits 20 minutes before another attempt; an in-flight claim expires after ten minutes. Any coverage progress suppresses another independent root, and the first fresh check resets the recovery state.

Coverage cadence (#802): GitHub's five-minute schedule for `launch-alert.yml` was measured to materialize only every ~2–8 hours, so coverage used to advance only after it went stale, producing a stale log, a 503 and a recovery dispatch about every 30 minutes. The same Neon invocation now also dispatches the same root ahead of time while coverage is still fresh but at least 20 minutes old, at most once per 15 minutes (`launch_watcher_cadence_dispatch_v1` in `settings`, compare-and-set). A cadence failure is logged as `launch_watcher_cadence_dispatch` and never fails the invocation. The 30-minute stale definition, the recovery path above and the operator alert are unchanged and remain the incident signal if coverage stops advancing.

The dispatch credential is `PACK1_LAUNCH_WATCHER_GITHUB_TOKEN`, a fine-grained GitHub token restricted to `killjoy00/mtg-ev-analyzer` with Actions write permission. It is stored in the protected `pack-one-mobile-release` GitHub Environment, injected only into the production `pack1growth` deployment, and intentionally absent from development. The guarded release validates its shape before backend changes, development smoke requires launch recovery to be unconfigured, and production smoke requires it to be configured. `/health` exposes only a boolean configuration marker, never the token. Rotate the token by replacing the protected environment secret and rerunning the guarded release; do not widen the token to repository administration or move it to a repo-wide secret.

The Neon invocation also owns an independent operator route, but routine automatic recovery is intentionally quiet. A durable `settings` state starts a 30-minute alert grace period when coverage first becomes stale. If the watchdog restores fresh coverage during that grace period, the state resets silently and no stale or recovery email is sent. If coverage remains stale through the grace period, the already-provisioned Pack One Resend credential sends one transactional stale notification to Pack One's established product/support mailbox, `admin@packone.pro`; repeated ten-minute stale checks deduplicate that episode. Recovery-dispatch failure, dispatch-state failure, or exhaustion of the bounded recovery attempts bypasses the grace period and sends the stale notification immediately. Fresh recovery always resets the operator state silently; there is no routine `Launch coverage recovered` email. The destination is the same public support mailbox documented for product support and store submission; the Auth deletion service-principal address is not used as an implicit alert recipient. Delivery is persisted as pending before the send and uses a deterministic provider idempotency key, so a failed or ambiguous send is retried without intentionally duplicating mail. Alert-delivery failure is itself logged.

The stale detector remains independent of GitHub schedule delivery even though the recovery action is authenticated to GitHub: detection runs on the Neon schedule, reads the sanitized public watermark, and does not depend on a GitHub Actions run being created first. It uses no production gameplay request, IP, player identity or QUOTA_KEY. If GitHub dispatch fails, the stale operator email and 503 remain observable through Neon. Manual deletion-maintenance recovery does not perform the stale check; only the independent Neon schedule does.

The watcher separately reads the last complete UTC day's production Worker requests and whole-project Neon compute/egress. It performs no SQL and does not keep computes awake. Daily Neon usage includes development and CI branches, is delayed, and is retained for operator context only; it does not route a production incident because the provider metric cannot attribute the usage to production. Release/PR `check` mode remains a current 15-minute verification and does not mutate the durable alert watermark.

Thresholds live in `scripts/launch-alert.mjs` and the gateway shares its latency boundaries through `launch-alert-policy.mjs`. The availability guard remains at least five 5xx and over 1% estimated requests per 15-minute window. Ten unclassified or network/application 429s remain an alert. Confirmed per-player mobile sign-in/signup limiter responses produce a separate `authentication_429` warning at ten events. Classification requires the protected origin's finite internal marker; incoming client headers, account-route guesses and unknown limits cannot downgrade an alert. The marker never reaches the browser, and no quota, counter, deadline or retry policy changes.

The gateway retains every response over five seconds or with a quota check over one second, every 4xx/5xx, and 10% of other successes. Each event carries its actual inclusion probability and a tail-sampling version. Weighted request estimates remain valid; latency counts are not multiplied by ten. Three retained slow requests or quota checks in a window produce diagnostic warnings. They escalate only after a continuous 30 minutes of breached five-minute endpoints on core gameplay/session routes, rather than multiple overlapping copies of a single burst. Admin/account-only slowness remains visible as a warning. Mixed old/new gateway releases are explicitly reported as `legacy_or_mixed`; their latency counts do not establish a comparable full-retention baseline or an SLO. Gateway timing ends at response construction, not at complete body transfer or browser rendering. Diagnostic categories are finite feature/failure classes, not request logs or identities.

Every alert-mode run still sends one `GET https://api.packone.pro/draft/health?quick=1` through the gateway's quota Durable Object and origin, retrying once after five seconds. If both attempts fail to return 200 with `ok: true`, `gateway_probe_failed` is routed and the run fails. This probe does no database query. GitHub schedule delivery and the independent Neon coverage dispatcher retain their existing cadence and recovery bounds; this is not a new 1-5-minute independent uptime service. Real-traffic log thresholds and the probe complement each other, and neither certifies complete gameplay health.

The watcher now reads and validates project billing-period compute/transfer counters on every usage pass, including when normal daily v2 history succeeds. The 200-CU-hour/200-GB (200,000,000,000 decimal bytes) operator warning thresholds apply to those cumulative whole-project observations, with exact period boundaries and explicit scope; daily compute/public egress stay report-only. Daily public egress and cumulative all-network transfer are different metrics and are never subtracted or relabeled. Missing/negative counters, wrong project identity or a stale/invalid billing period fail visibly. Daily history still uses the existing bounded 403/404 fallbacks. Provider observation time does not prove that accounting has settled.

Set repository variable `PACK1_WORKERS_PLAN` only after verifying the actual account subscription (`free` or `paid`). Unknown/unconfigured plans preserve the 100,000-requests-per-complete-day volume warning, without calling it an outage. Paid-plan daily volume is report-only. For Free, a separate account-wide current UTC-day query warns at 80,000 requests and alerts at 95,000, allowing headroom before the 100,000 daily allowance; the provider may report with delay. These are not instantaneous or gateway-only counters. No billing permission, provider secret or subscription is changed. Truncated, malformed or inaccessible telemetry fails the check; a partial query is never silently marked covered.

Incidents use one open issue per category, without person assignments or repeated comments. Titles distinguish `[launch alert]`, `[launch warning]` and `[launch recovered]`; existing category issues are reused, including across paginated issue lists. A small allowlisted lifecycle marker records first/last breached window ends, observed episodes, current/worst severity, and `active`, `recovering`, `recovered` or `unknown` status. Existing evidence is retained. New issue bodies contain category/status and operating instructions, not detailed production telemetry. Recovery requires a fully inspected, persisted, current coverage target and 30 minutes beyond the last bad window; incomplete monitoring reports `unknown` rather than recovery. A successful explicit probe proves probe recovery. A recovered issue stays open for investigation, and a new breach updates the episode rather than being silently swallowed. Unchanged healthy states do not produce polling edits. `pause_outreach` is based on currently active alert-severity conditions, not a historical replay breach or a warning. Check that field and current incident status before resuming outreach; absence of a current breach does not identify its cause.

Whole-project daily Neon compute/egress observations never create production incidents. Existing GitHub report retention and the independent Neon stale email route remain in place; no private-routing migration or recipient change is included. Do not publish expanded diagnostics or private source logs in an issue. `coverage_pending`, `coverage_continuation_failed` and cleanly recovered `telemetry_unavailable` incidents retain automatic closure; threshold, probe, usage and unrecoverable-coverage incidents remain operator-closed. A long-lived warning never suppresses an independent availability or monitoring failure. Issue #541 remains billing-period usage context only; #596 remains the unchanged coverage watermark. PR validation is offline and cannot post incidents. Zero retained events do not prove production instrumentation works; verify release-tagged events after the guarded gateway rollout.

## Egress recovery evidence (#541)

Use the `Egress recovery evidence` workflow (`egress-recovery.yml`) for a read-only provider observation. It runs on relevant PRs/main changes, by manual dispatch, and on a requested daily 15:43 UTC schedule. It retains `neon-egress-evidence/report.json` artifacts for 90 days and compares with the previous successful main observation. It makes bounded Neon metadata/history GET requests only: no SQL, corpus payload download, compute wakeup, resize or branch mutation. See `docs/reports/egress-recovery-2026-09-26.md` for the initial evidence and known limitations.

Always record provider, project/branch identity, exact metric, unit, scope, billing-period boundaries, collection timestamps and delta. `project.data_transfer_bytes` is a whole-project billing-period counter including production, development and CI; do not call it daily production traffic or subtract public-only history from it. `observed_at` is the collection time, not a provider consumption watermark. An unchanged counter proves only an unchanged reported counter, not zero actual traffic or settled recovery. Missing/incomplete/paginated history is not zero usage, and unowned/deleted branches prevent complete CI attribution. Do not assign the project-minus-visible-branches remainder to CI.

The evidence collector rejects comparisons across period, scope, metric or identity changes. A decreased counter within a period is an uncomparable provider correction/reset, never negative usage. A new billing period establishes a new baseline; wait for a second comparable observation for an interval delta. The history request excludes two recent hours and starts after the first complete post-fix UTC hour; that allowance is not a guarantee that provider accounting has settled. HTTP 403/404 history responses are retained as unavailable. Authentication, rate-limit and server failures remain visible failures.

Do not close #541 solely because the earlier no-op scan was fixed or because the counter stopped changing. The egress warning threshold was increased at owner request on October 27, 2026, from 50 GiB to 200 GB (200,000,000,000 decimal bytes), applying to the provider's cumulative whole-project billing-period transfer counter. This changes only the operator warning threshold: it does not change Neon billing allowances, consumption, or the compute threshold. After rollout, verify the watcher reports the new threshold and that the former egress warning is recovered; close #1338 only with this change documented, not as evidence of lower consumption. Keep the evidence collector's distinct 5-GiB daily threshold and independent error/latency/quota/coverage incidents unchanged. No automatic closure is performed by the evidence workflow.

## Responding to a launch incident

1. Pause outreach and further load escalation. Inspect the watcher artifact, exact gateway release, latest secure-auth release, and load artifacts. Do not repeat mutations as diagnostic probes.
2. For 429s, inspect `quota_scope` and backend status. Request/session network limits indicate shared-network pressure or abuse; application 429s can be per-player/account limits. Do not rotate QUOTA_KEY to clear counters. Confirm legitimate shared-network traffic before proposing a policy change, and rerun the NAT and runtime gates.
3. If `quota_ms` is high, inspect Durable Object latency and errors. If `upstream_ms` dominates, inspect Neon Functions latency, compute state/size and database query plans. The five-second quota deadline and 120-second shared origin deadline bound requests; they are not latency targets.
4. A practice-cache refresh can return retryable 503 with Retry-After. Use `scripts/warm-practice-cache.mjs` through the guarded release/maintenance workflow, verify the current serving revision, and investigate bulk imports or policy changes that invalidated it. Do not bypass serving quality or silently use stale inventory.
5. For usage alerts, inspect the corresponding complete UTC day and separate production from disposable branch activity in Neon. Stop optional experiments and remove expired disposable branches after ownership verification. Do not downsize live compute during an incident without evidence.
6. Restore the last known-good reviewed Functions/gateway revision through the secure-auth release workflow if the new release caused errors. Deploy compatible backend Functions before the gateway. Keep additive migrations 0038/0039 and the existing QUOTA_KEY; do not drop cache tables or roll back corpus data as an application rollback. Verify cookie refresh, a guest Daily, release identity and alert query access afterward.

Public leaderboard/profile caching remains conditional on measured cost. Cached public results would need strict separation from authenticated self-profile responses, short explicit TTLs and purge semantics. Do not cache account/session or run mutation responses. Retained fixture plans and measured route latency determine whether that work is necessary for the declared launch target.

## Browser script errors

The main site (`index.html` via `bootstrap.mjs`) reports uncaught script errors and unhandled promise rejections as `client_error` product events through the existing `/v1/events` pipeline. Each event carries only `kind` (`error` or `rejection`), `context` (the message with URLs and email addresses replaced, 100 characters), `type` (same-origin `file:line:column`, or `(unknown)` for rejections), `surface` (page path without query or hash), plus the usual allowlisted game `mode`/`set` and browser-session id. Extension, third-party and opaque cross-origin errors, and offline/aborted/timed-out requests are not reported; a page sends at most five distinct reports. Server and gateway monitoring above remains the authority for API availability; these events show what broke in players' browsers.

Review after a release or a player report:

```sql
SELECT event_props->>'type' AS location, event_props->>'context' AS message,
       event_props->>'kind' AS kind, count(*) AS events, count(DISTINCT player_id) AS players,
       min(created_at) AS first_seen, max(created_at) AS last_seen
FROM analytics_events
WHERE event_name='client_error' AND created_at > now() - interval '7 days'
GROUP BY 1,2,3 ORDER BY players DESC, events DESC LIMIT 50;
```

The native apps do not report script errors yet; adding it changes the App Store privacy and Google Play Data Safety declarations.

## Rejected account and player sessions

The Growth function logs one JSON line per rejected session instead of a stack trace: `player_session_rejected` and `account_session_rejected` (401s, #803) and, since #1138, `account_csrf_rejected` (the web Account page's “Account request could not be verified.” 403). Each line carries only `event`, `reason`, a path with ids replaced by `:id`, a client class (`browser`, `native_account` or `no_origin`) and `release_commit`. Tokens, cookies and account identifiers are never logged. These lines live only in the Neon console's logs for the Growth function; nothing alerts on them. When a player reports the Account error, filter those logs for `account_csrf_rejected`: `missing` means the page could not read its security cookie, `invalid` means the cookie was malformed, and `mismatch` means the cookie belongs to a different session than the account cookie.
