# Launch response and usage controls

The production launch watcher requests a five-minute GitHub Actions schedule, but GitHub schedules are not a delivery guarantee. Alert-mode runs therefore persist a sanitized gateway-log coverage watermark in issue #596 (`[launch watcher] Coverage state`) instead of assuming the current run arrived on time. Each threshold calculation is still exactly a 15-minute window: window endpoints advance in five-minute steps, a two-minute settlement delay avoids treating the newest log edge as complete, a first run bootstraps two hours, and every later run replays the most recent 30 minutes for late log arrival before moving forward. Catch-up remains bounded to 30 new windows (2.5 hours) per run. If a run ends with recoverable backlog, it routes a `coverage_pending` incident and immediately dispatches the same workflow as a serialized continuation instead of waiting for another best-effort cron delivery. Continuations preserve the existing concurrency group, increment a reviewed depth counter, and stop after 12 chained passes. Dispatch failure or depth exhaustion routes `coverage_continuation_failed` and fails the run; the next independent schedule can start a new bounded chain. The recoverable coverage incidents close automatically once no corresponding condition remains.

Coverage advances only through the last fully inspected new window. A failed, truncated, schema-invalid or inaccessible replay/catch-up interval stops forward progress; a later run starts from the durable watermark again. The workflow's concurrency group serializes alert-mode executions, and the state update re-reads and monotonically merges the issue body so a stale writer cannot move the watermark backward or erase recorded alert-window evidence. Duplicate retained events are keyed by Cloudflare event ID inside each query. Recent successful windows are deliberately replayed so an event that arrives late can still breach its original 15-minute threshold.

Workers Logs retention is plan-limited. The watcher uses the documented three-day minimum retention as a conservative recoverability bound even if the account may retain more. If the first missing 15-minute calculation requires logs older than that bound, the run reports `coverage_unrecoverable`, does not advance across the gap, routes a category-specific incident, and fails. Operators must not infer healthy coverage from a later current-window query after such a gap.

The existing independent Neon `pack1-account-deletion-maintenance` Function Trigger also checks the public sanitized coverage watermark after its deletion-maintenance work. If issue #596 is absent/invalid/inaccessible or `covered_through` is more than 30 minutes behind the trigger's edge-attested scheduled time, `pack1growth` logs a structured `launch_watcher_stale` event and returns 503 for that trigger invocation. The same Neon invocation owns an independent operator route: a durable `settings` state records the stale episode, the already-provisioned Pack One Resend credential sends one transactional stale notification to the configured deletion-admin mailbox, repeated ten-minute stale checks deduplicate that episode, and the first fresh check sends one recovery notification. Delivery is persisted as pending before the send and uses a deterministic provider idempotency key, so a failed or ambiguous send is retried without intentionally duplicating mail. Alert-delivery failure is itself logged; if coverage is fresh but the recovery notification cannot be delivered, the trigger returns 503 so the pending recovery is retried. This check and alert route use no GitHub credential, production gameplay request, IP, player identity or QUOTA_KEY, so GitHub's watcher cannot hide its own scheduling absence. Manual deletion-maintenance recovery does not perform the stale check; only the independent Neon schedule does.

The watcher separately reads the last complete UTC day's production Worker requests and whole-project Neon compute/egress. It performs no SQL and does not keep computes awake. Daily usage includes CI branches on Neon, is delayed, and is an investigation threshold, not a billing cap or dollar forecast. Release/PR `check` mode remains a current 15-minute verification and does not mutate the durable alert watermark.

Thresholds live in `scripts/launch-alert.mjs`: at least five 5xx and over 1% estimated requests, ten 429s, three sampled requests over five seconds, or three sampled quota calls over one second per 15-minute window; 100,000 Worker requests, 24 CU-hours or 5 GiB Neon public egress per complete day. If v2 consumption metrics are unavailable (403/404), use the documented legacy daily compute history and project billing-period transfer counter, with a separate 50-GiB billing-period threshold. If both history APIs are unavailable, use project billing-period compute/transfer counters with separate 200-CU-hour/50-GiB thresholds. Never relabel cumulative counters as daily usage; the report names the source and period. Successes are sampled at 10%, errors at 100%; rates are weighted estimates, not exact percentiles. Low-volume sampled latency cannot establish an SLO. Truncated queries split into bounded windows; exhaustion or access/schema failure fails the check and opens a telemetry-unavailable incident.

Alerts use one open repository issue per condition titled `[launch alert] Production capacity needs attention (<condition>)`, without person assignments or repeated comments. GitHub Actions failures, `coverage_pending`/`coverage_continuation_failed` issues, and the independent Neon stale email expose watcher failures through different scheduling/delivery substrates. Detailed sanitized reports are retained for 14 days. `coverage_pending` and `coverage_continuation_failed` close automatically after recovery; threshold, usage, telemetry and unrecoverable-coverage incidents remain operator-closed after investigation so a later incident can create a new alert. A long-lived usage warning never suppresses a new error, quota, latency, missing-telemetry or unrecoverable-coverage incident. Issue #541 remains billing-period usage context only; it is not the coverage-watermark incident. PR checks verify read access without posting incidents. The watcher can run before the gateway rollout; zero retained gateway events at that stage does not prove production instrumentation works. Verify retained release-tagged events after rollout.

## Egress recovery evidence (#541)

Use the `Egress recovery evidence` workflow (`egress-recovery.yml`) for a read-only provider observation. It runs on relevant PRs/main changes, by manual dispatch, and on a requested daily 15:43 UTC schedule. It retains `neon-egress-evidence/report.json` artifacts for 90 days and compares with the previous successful main observation. It makes bounded Neon metadata/history GET requests only: no SQL, corpus payload download, compute wakeup, resize or branch mutation. See `docs/reports/egress-recovery-2026-09-26.md` for the initial evidence and known limitations.

Always record provider, project/branch identity, exact metric, unit, scope, billing-period boundaries, collection timestamps and delta. `project.data_transfer_bytes` is a whole-project billing-period counter including production, development and CI; do not call it daily production traffic or subtract public-only history from it. `observed_at` is the collection time, not a provider consumption watermark. An unchanged counter proves only an unchanged reported counter, not zero actual traffic or settled recovery. Missing/incomplete/paginated history is not zero usage, and unowned/deleted branches prevent complete CI attribution. Do not assign the project-minus-visible-branches remainder to CI.

The evidence collector rejects comparisons across period, scope, metric or identity changes. A decreased counter within a period is an uncomparable provider correction/reset, never negative usage. A new billing period establishes a new baseline; wait for a second comparable observation for an interval delta. The history request excludes two recent hours and starts after the first complete post-fix UTC hour; that allowance is not a guarantee that provider accounting has settled. HTTP 403/404 history responses are retained as unavailable. Authentication, rate-limit and server failures remain visible failures.

Do not close #541 solely because the earlier no-op scan was fixed or because the counter stopped changing. The existing billing-period warning remains active above 50 GiB (53,687,091,200 bytes). After the provider reports the new period, verify that the usage condition actually clears and retain a meaningful comparable post-remediation interval, recording any remaining freshness/attribution limit. A reset alone is not proof of remediation. Keep the 5-GiB daily threshold, 50-GiB billing threshold and independent error/latency/quota/coverage incidents unchanged. No automatic closure is performed by the evidence workflow.

## Responding to a launch incident

1. Pause outreach and further load escalation. Inspect the watcher artifact, exact gateway release, latest secure-auth release, and load artifacts. Do not repeat mutations as diagnostic probes.
2. For 429s, inspect `quota_scope` and backend status. Request/session network limits indicate shared-network pressure or abuse; application 429s can be per-player/account limits. Do not rotate QUOTA_KEY to clear counters. Confirm legitimate shared-network traffic before proposing a policy change, and rerun the NAT and runtime gates.
3. If `quota_ms` is high, inspect Durable Object latency and errors. If `upstream_ms` dominates, inspect Neon Functions latency, compute state/size and database query plans. The five-second quota deadline and 120-second shared origin deadline bound requests; they are not latency targets.
4. A practice-cache refresh can return retryable 503 with Retry-After. Use `scripts/warm-practice-cache.mjs` through the guarded release/maintenance workflow, verify the current serving revision, and investigate bulk imports or policy changes that invalidated it. Do not bypass serving quality or silently use stale inventory.
5. For usage alerts, inspect the corresponding complete UTC day and separate production from disposable branch activity in Neon. Stop optional experiments and remove expired disposable branches after ownership verification. Do not downsize live compute during an incident without evidence.
6. Restore the last known-good reviewed Functions/gateway revision through the secure-auth release workflow if the new release caused errors. Deploy compatible backend Functions before the gateway. Keep additive migrations 0038/0039 and the existing QUOTA_KEY; do not drop cache tables or roll back corpus data as an application rollback. Verify cookie refresh, a guest Daily, release identity and alert query access afterward.

Public leaderboard/profile caching remains conditional on measured cost. Cached public results would need strict separation from authenticated self-profile responses, short explicit TTLs and purge semantics. Do not cache account/session or run mutation responses. Retained fixture plans and measured route latency determine whether that work is necessary for the declared launch target.
